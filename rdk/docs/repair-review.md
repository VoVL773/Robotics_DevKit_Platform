# 修复任务单评审与实施边界

本说明对应 2026-11-05 的外部修复建议。任务单中的问题描述须以仓库现状和真实验收为准，
不能将 mock 测试通过等同于跨发行版构建或完整离线构建通过。

## 首批修复

- **T7：版本来源。** CLI 展示、项目来源记录、容器导出的项目元数据统一读取安装包版本。
  环境定义版本独立来自 profiles；源码未安装时返回 `0.0.0+unknown`。
- **T5：失败诊断。** 构建和验收实时转发原始输出，失败后追加可识别的包版本、源配置和网络建议。
  当前没有 `env lock-check` 命令，提示使用现有命令，不引用尚未实现的入口。
- **T8：解释器。** 从 PATH 发现解释器并验证 ROS 模块；隔离 venv 不可用时只尝试其自身报告的基础解释器。
  单纯采用 `which('python3')` 已在激活项目 venv 的实测中暴露 `catkin_pkg` 缺失，因此不能原样采用。
- **T1：模板守卫。** 保留两个已发布版本。除 manifest 外逐文件比较内容摘要，
  仅将已存在的 Jazzy/双发行版 README 文案转换为同一形式；README 其他变化仍会失败。
  用临时模板副本注入 CMake、README 和新增文件变动，验证诊断包含相对路径。

## 锁格式与预检（T3、T4）

schema 2 应在保持现有 `profile`、`base_digest`、`with_torch`、`files` 兼容性的基础上增加包记录，
不要仅凭新 JSON 示例移除旧字段。来源与哈希无法证明时应为 `null`，同时说明缺失原因。
APT 的配置源列表和某个具体包实际选中的来源是两类信息，不能混用。
pip 来源须保留真实索引与环境标记，特别是 CPU/CUDA PyTorch，不能统一标成 PyPI。
schema 1 的读取保留原有文件摘要检查并给出迁移提示；警告不得破坏 `--json` 的标准输出。

预检必须以目标 profile 的系统版本、架构和源配置为查询上下文。宿主机 `apt-cache` 默认索引
不能直接用来判断另一发行版的锁。只安装了某版本也不能证明远程源仍提供该版本。
实现前需确定目标源索引如何获取、验证和更新，以及结果的时间范围。
命令本身只读，不安装软件、不要求 Docker；查询失败或缺少目标源索引应作为检查失败报告，
不得误报成包被移除或全部可用。当前源可用性也不意味着未来仍可用。

CI 的 Humble/Jazzy 预检应使用各自匹配的源上下文。定时任务和 PR 快速检查的范围需要分别定义，
不能增加一个 schedule 字段就让原有所有昂贵 job 一起每周运行。

## 更新锁与依赖求解（T6）

保留全量刷新能力，但修改现有 `--update-lock` 语义前必须同步检查 configure、build、init、
TUI 调用方以及“CLI 源码改变”“with_torch 改变”等已有更新场景，不能只增加一个命令参数。

最小更新需要固定原基础镜像、公钥以及其他包版本，再交给目标环境中的依赖求解器验证事务。
包之间有依赖，不能将新旧版本字符串直接拼接成锁；没有兼容解时失败并保留旧上下文，
不能静默放开其他版本约束。包在源中彻底消失时也不能擅自从依赖中删除。

只有求解、下载校验和上下文生成全部成功后才替换锁。保存前后快照和 diff，并区分新增、移除、
升级、降级、来源变化；历史文件命名应避免同一秒内多次操作覆盖。
`last_verified_at` 等可变验收信息应与构建身份分离，否则仅更新验收时间就会改变镜像标签。

## 字节归档与离线验收（T10）

完整离线构建需要三部分：本机已有 digest 匹配的基础镜像、完整 APT 事务的 deb、
匹配目标 Python/架构的 wheels（包括构建工具和显式启用的训练依赖）。仅有 deb 不足以完成当前 Dockerfile。
解析与下载应在目标 profile 的上下文中执行，不能让 Jazzy 宿主机替 Humble 解析依赖或 Python 标记。

归档必须从已验证的软件源获取，核对包名、版本和架构，记录实际文件摘要；归档后回写锁和上下文摘要应一致。
构建前重新验证文件摘要，不以可修改的本地索引作为唯一信任依据。
下载失败保留已成功的文件，但整体失败且不能留下“归档完整”的标记。

离线构建应显式禁用远程 APT 源、使用 wheels 的 `--no-index`，并限制 Docker 构建步骤的网络。
基础镜像未缓存、缺 deb/wheel、哈希不匹配时分别给出具体错误；禁止静默联网补齐。
APT 本地源写在前面不能替代这些约束。只有在禁网条件下无缓存地实际构建成功，才能宣称完整离线验收通过。

## 模板存储与 CI（T2、T9）

当前 `-1.1` 是目录后缀，manifest 中的模板名称始终是 `ros2-cpp` 等规范名。
`ros2-cpp@1.0.0` 和 `ros2-cpp@1.1.0` 已支持独立解析，不能通过删除目录破坏旧引用。
如需去重，优先设计“版本 manifest + 共享资源”的机制，保留旧版本的参数限制、文档和可重复生成行为。
发行版差异由生成时的 profile 派生，并验证参数不能组成互相矛盾的发行版/Python/系统组合。
现有 CI 生成器已经切换 Humble/Jazzy 容器和宿主 runner，不需要重新实现相同逻辑。

完整镜像构建可移到手动和定时路径，但首先要测量各 job 实际耗时与失败覆盖。
PR 快速检查继续覆盖单测、wheel 安装和模板生成；是否加入在线源预检应明确其外部服务失败策略。
不能在没有 CI 运行记录时承诺十分钟以内完成。
